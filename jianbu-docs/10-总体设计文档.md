## 1. 系统概述

### 1.1 背景与目标
面向"全县工会会员"开展**健步走线上活动**：会员通过 H5 报名页报名，在微信小程序每日同步微信运动步数打卡，按积分排名，活动结束后发放奖励与电子证书；管理员在后台维护组织机构、管理报名、统计排行、处理异常与作弊账号。

### 1.2 一句话架构
**「H5 报名 → 小程序打卡 → 后端算分 → 后台管榜颁奖」**，五个部分围绕一张活动闭环协同。

### 1.3 系统组成部分

| 端 | 载体 | 使用者 | 定位 |
|---|---|---|---|
| ① H5 报名页 | 手机浏览器（`jianbu-h5/register.html`） | 全县工会会员 | **唯一报名入口**：查看活动/奖项、提交报名、草稿自动保存 |
| ② 微信小程序 | 微信（`jianbu-app`，uni-app Vue3） | 已报名会员 | **打卡/榜单/奖励/证书**：不含报名入口 |
| ③ 后台管理系统 | 浏览器（`plus-ui`，Vue3 + Element Plus） | 系统管理员/管理员 | 组织机构、活动、报名、会员、统计、作弊处理、中奖名单 |
| ④ 后端服务 | Java（RuoYi-Vue-Plus 5.6.0 新增 `ruoyi-walking` 模块） | — | 全部业务规则执行者，三端共用 |
| ⑤ 数据存储 | MySQL 8（`ry-vue` 库 `walking_*`）+ Redis | — | 业务数据 + 缓存/会话 |

> **分工红线**：业务规则（积分/断卡/封顶/锁榜/作弊判定）**只在后端执行**，H5 与小程序仅负责采集、展示和引导。身份规则见下。

## 3. 组成部分详解

### 3.1 ① H5 报名页（`jianbu-h5/register.html`）
**结构**：活动横幅 → 活动信息卡 → 奖项设置卡 → 会员资格说明（获奖须为工会会员）→ 报名表单（单位下拉 / 姓名 / 手机号）→ 提交按钮。

**关键行为**：
- 活动信息来自公开接口 `/activity/current`；单位下拉来自 `/org/list`（仅 `dept_category='union'`）。
- 表单输入 **600ms 防抖自动存草稿**（localStorage）；审核未通过自动恢复草稿，无需重填。
- 提交走 `/registration/submit` → 后端**自动审核**（字段校验 + 手机号唯一 + 内容安全）→ 通过 `status≥2` 清草稿提示成功；未通过展示 `auditResult` 修改提示。
- 一个手机号限报名一次；单个微信仅绑一个手机号（提示文案常驻表单下方）。

### 3.2 ② 微信小程序（`jianbu-app`）
五个页面：首页（打卡主战场）、排名、奖励、我的 + 登录页（详见 `09-小程序设计文档`）。
- **登录**：静默 `uni.login` → `/member/login` 换 openid → 绑定报名手机号 → 匹配报名记录才放行。
- **打卡**：打开自动拉取微信运动（授权后）；已同步展示今日步数/达标；日历展示当月打卡。
- **规则展示**：封顶 15000、达标 7000、断卡、缓冲期、锁榜等**一律由后端判定，前端仅展示**。

### 3.3 ③ 后台管理系统（`plus-ui` 新增 `src/views/walking/`）
| 菜单 | 页面 | 权限码 |
|---|---|---|
| 健步走活动 | `activity/index.vue` | `walking:activity:*` |
| 报名管理 | `registration/index.vue` | `walking:registration:list/cancel/disable/dept` |
| 会员管理 | `member/index.vue` | `walking:member:list/edit` |
| 数据统计 | `stat/index.vue` | `walking:stat:list` |
| 作弊处理 | `cheat/index.vue` | `walking:cheat:list/handle` |
| 中奖名单管理 | `award/index.vue` | `walking:award:list/query/mark/remove/export` |
| 奖励管理 | `awardConfig/index.vue` | `walking:awardConfig:list/query/add/edit/remove`（修改后 H5 报名页 + 小程序奖励页即时生效） |
| 组织机构 | 复用"部门管理"（`sys_dept`） | `system:dept:*` |

角色：**系统管理员**（全部）+ **管理员**（细分权限，如中奖标记默认不给）。路由/按钮由后端 `sys_menu` + 权限码驱动。

### 3.4 ④ 后端服务（`ruoyi-walking` 模块）
目录（详见 `04-开发设计` 2.1）：
- `controller/`：公开（Activity/Org）+ 会员（Member/Registration/Step/Ranking/Award/Certificate）+ `admin/`（Activity/Registration/Member/Stat/Cheat/Award）
- `service/`：业务引擎（自动审核 / 积分与连续打卡 / 作弊检测 / 证书生成）
- `wx/`：WxService（code2Session / WeRunData 解密 / msgSecCheck / access_token 缓存）
- `filter/`：本地敏感词过滤（开发期），上线切微信内容安全
- 定时任务：每日凌晨统计积分 + 刷新榜单 + 活动结束次日 0 点锁榜

### 3.5 ⑤ 数据存储（见 `02-数据库设计`）
- 9 张业务表：`walking_activity / member / registration / step_record / points / award / certificate / cheat_log / audit_log`
- 扩展列：`walking_activity` 增加 `daily_step_limit / streak7_points / streak14_points / full_attendance_points / buffer_days`；`walking_certificate` 增加 `award_level`（`walking_config_award.sql`）
- 复用若依表：`sys_dept`（工会组织树，`dept_category='union'`、`walking_member_total` 会员总数）、`sys_user`/`sys_menu`/`sys_role`（后台）
- Redis：会话 token、榜单缓存、积分/同步并发控制

## 4. 核心业务流程（端到端）

### 4.1 全生命周期

```
【报名期】                                【打卡期】                              【结算期】
会员打开 H5 → 查看活动/奖项 → 填表单       会员打开小程序 → 静默登录               活动结束
  → 提交 → 后端自动审核 → 通过(锁定姓名/     → 绑报名手机号(身份匹配)               ┌ 缓冲期(仅同步历史步数,
    手机号) → 报名成功进入活动               → 每日: 自动同步微信运动步数             不计积分/不更新榜单)
  └ 未通过 → 提示修改(草稿已存)             → 后端: 过滤/封顶15000/达标7000        │
                                          → 积分累计 + 连续打卡奖励              └ 结束次日0点 → 统一锁榜
                                          → 榜单/排名                              → 生成名次 → 颁奖(中奖名单)
                                                                                  → 生成电子证书 → 会员填收货地址
```

### 4.2 报名 → 身份验证流程（关键链路）
```
H5 提交报名（姓名/单位/手机号）
  └→ 后端自动审核（字段 + 手机号唯一 + 内容安全）→ status: 0草稿→1→2通过（锁定姓名/手机号）
小程序首次打开
  ├→ uni.login → /member/login → 建/查 openid 会员
  ├→ 绑定手机号 /member/phone → 校验唯一 + 匹配 walking_registration
  │    └→ 匹配到报名(status=2) → 放行进入首页
  └→ 未匹配 → 提示"尚未报名，请先到报名页报名"
```
> **身份桥梁 = 手机号**：小程序不重新报名，仅验证「绑定手机号」与「报名记录手机号」一致即放行（`05` 2.5 节）。

### 4.3 步数打卡 → 积分 → 排名流程
```
小程序打开 → 授权微信运动 → getWeRunData(encryptedData, iv)
  └→ POST /step/sync
       ├→ 后端解密 → 校验活动期/报名前过滤/当日封顶 15000（超量丢弃）
       ├→ upsert walking_step_record（会员+活动+日期 唯一）
       ├→ 判定达标（≥7000 且当日有同步）→ 当日积分 = 基础分
       ├→ 连续打卡判定（断档归零）→ 7/14/21 天阶段奖励（幂等，次数上限）
       └→ 作弊检测 → abnormal_flag 标记 + 审计日志
每日凌晨定时任务 → 汇总积分 + 刷新总榜/积分榜 → walking_points
排名口径：总积分 DESC → 连续天数 DESC → 总步数 DESC
缓冲期：步数只同步，不计积分不更新榜单
活动结束次日 0 点 → 锁榜（数据永久固化）→ 颁奖 + 生成证书
```

### 4.4 作弊与异常处理流程（管理员）
```
后端标记 abnormal_flag=1（步数超限/活动期外/突增>均值3倍）
管理员后台查看异常列表 → 选择处理方式：
  ① 仅标记  ② 删除异常步数（连积分撤销）  ③ 停用账号(+报名停用)  ④ 取消报名
→ 全部写入 walking_cheat_log 审计留痕（操作人/时间/备注）
```

## 5. 关键设计决策（含理由）

| # | 决策 | 理由 |
|---|---|---|
| D1 | **身份桥梁用手机号，不重建会员体系** | H5 无法拿到微信身份，小程序静默登录后只能靠"报名手机号"匹配，避免重复报名与信息不一致 |
| D2 | **业务规则全部后端执行，前端只展示** | 防止前端绕过封顶/断卡/锁榜；单一口径，改规则不动端 |
| D3 | **微信能力可开关切换（开发期模拟 → 真号切换）** | AppID 未到手也能全链路联调：`dev_test_*` 模拟 openid、`steps` 直传、本地敏感词；换真号仅改配置（`06`） |
| D4 | **小程序不含报名入口** | 报名是低频一次性动作，走 H5 更简单（免审核、免扫码授权）；小程序聚焦高频打卡 |
| D5 | **积分非实时，凌晨统一结算 + 管理员手动刷新** | 受微信步数同步机制限制（次日才同步完整）；避免实时重算的性能与一致性成本（`07` 三节） |
| D6 | **缓冲期 + 次日 0 点锁榜** | 给用户补同步窗口，同时明确结算边界：缓冲期步数有效但不计分，锁榜后数据永久固化（`08`） |
| D7 | **审核通过即锁定姓名/手机号，管理员可调单位/地址** | 报名信息是颁奖/证书依据，防止用户赛后篡改；单位变更属于管理员职权 |
| D8 | **排名基于 walking_points 汇总，连续天数基于 step_record 计算** | 积分流水可追溯（加分/扣分/奖励），榜单口径清晰（`07` 四节） |
| D9 | **复用若依底座（sys_dept 组织树 / sys_user 后台账号 / sys_menu 驱动路由 / 代码生成器）** | 不重复造轮子：组织树天然支持三级工会、后台权限零改前端 |
| D10 | **证书纯视图层动态填充，不做图片合成** | 姓名/单位/等级/日期变化即时生效，无需重新生成图片（`09` 4.3） |

## 6. 模块划分与职责边界

| 模块 | 职责 | 不做什么 |
|---|---|---|
| H5 报名页 | 采集报名信息、展示活动/奖项、存草稿 | 不做打卡/榜单/登录 |
| 小程序 | 采集步数、展示数据、引导授权 | 不计算积分、不判达标、不封顶 |
| 后台 | 数据管理、审核、统计、处理异常、颁奖 | 不参与打卡数据计算 |
| 后端 | 全部规则执行 + 鉴权 + 数据落库 | 不做前端展示 |
| 数据库 | 数据存储与一致性约束（唯一键） | — |

## 7. 安全设计

| 维度 | 方案 |
|---|---|
| 会员鉴权 | Sa-Token，`POST /member/login`（code2session 换 openid）发 token；会员会话与后台会话区分登录类型 |
| 管理端鉴权 | `@SaCheckPermission("walking:xxx:xxx")` + 角色（系统管理员/管理员） |
| 公开接口 | `@SaIgnore`（活动查询 / 组织机构 / 登录），仅只读 |
| 内容安全 | 开发期本地敏感词过滤；上线 `wx.content-check.enabled=true` 调微信 `msgSecCheck` |
| 防作弊 | 单日上限 / 活动期外 / 突增检测 + 审计留痕；来源字段防伪造（小程序端只允许 source=1） |
| 接口加密 | 若依 `api-decrypt` 开关（前后端需一致，生产建议开启） |
| 隐私 | 手机号脱敏展示；openid 不对外；AppSecret 不入库不进 git（`06`） |
| 锁榜防篡改 | 活动结束次日 0 点锁榜，历史数据固化不可改 |

## 8. 非功能设计

| 项 | 设计 |
|---|---|
| 性能 | 榜单 Redis 缓存；`SUM(steps)` 聚合走 `idx_step_activity_date` 索引；分页查询 |
| 一致性 | 唯一键兜底：会员 openid/phone、报名 (member,activity)、步数 (member,activity,date)、证书 (member,activity)；积分幂等（同一周期不重复发） |
| 定时任务 | 复用若依定时任务：每日凌晨积分结算 + 榜单刷新 + 锁榜 |
| 并发 | Redis 锁防同日重复同步/重复发奖 |
| 可用性 | 小程序各卡片独立加载，弱网降级不白屏；H5 零依赖静态页 |
| 审计 | 作弊处理、审核、取消/撤下全部落 `walking_cheat_log` / `walking_audit_log` |
| 可扩展 | 活动表参数化（封顶/奖励分/缓冲期均可配）；后续活动只需新建 `walking_activity` |

## 10. 数据设计总览（详见 `02-数据库设计`）

```
sys_dept（工会组织树, dept_category='union'）
   │1:N
walking_member ──1:N── walking_registration N:1── walking_activity
    │                                                        │1:N
    ├─ walking_step_record ◄──(会员+活动+日期唯一)──────────┼── walking_points
```

## 12. 测试与验收要点

1. **身份链路**：H5 报名 → 小程序绑同一手机号放行；绑错号/未报名 → 引导提示。
2. **打卡链路**：授权 → 自动同步 → 达标判定 → 积分增加；封顶 15000 生效。
3. **规则链路**：断卡中断、7/14/21 天奖励、重复发奖幂等、次数上限。
4. **锁榜链路**：缓冲期不计分 → 结束次日 0 点锁榜 → 数据固化。
5. **作弊链路**：超限/突增标记异常 → 管理员删除/停用 → 审计可查。
6. **后台链路**：活动 CRUD、报名取消/撤下/调单位、统计报表、中奖名单导出。
7. **安全**：未登录访问会员接口被拒；无权限按钮不可见；内容安全拦截。
8. **可用性**：弱网/后端未启动时各端不白屏，有兜底提示。
